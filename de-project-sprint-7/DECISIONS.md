# Особенности и технические решения

## Витрина пользователей

### Определение home_city
home_city — домашний адрес пользователя. Это - "последний город, в котором пользователь был дольше 27 дней".

Выбранный подход:
пользователь был в городе ≥27 дней, если каждый день из этих 27+ дней он писал хотя бы одно сообщение из этого города.

Алгоритм
1. Для каждого пользователя и каждого города собрать даты (date) 
   его сообщений.
2. Разбить даты на непрерывные цепочки:
   - последовательные даты без пропусков;
   - пропуск хотя бы одного дня → новая цепочка.
3. Оставить цепочки длиной ≥27 дней.
4. Для каждого (user_id, city) взять последнюю (по времени) 
   подходящую цепочку.
5. Из всех подходящих городов пользователя выбрать тот, у которого 
   max(date) последней цепочки — самый поздний.
6. Это и есть home_city — «последний город, где пользователь был 
   ≥27 дней».

Обоснование выбора
1. Единственный надёжный сигнал о местоположении 
   пользователя — это его сообщения. Если пользователь пишет из города 
   каждый день 27 дней подряд, он точно находится в этом городе 
   (или регулярно в него возвращается). В отличие от подхода «разница 
   между первым и последним сообщением», здесь нет «дыр», в которые 
   пользователь мог уехать в другой город.
2. Формулировка «был дольше 27 дней» 
   требует непрерывного подтверждения присутствия. «Каждый день 
   ≥1 сообщение» — это и есть непрерывное подтверждение.
3. Не нужно решать, что считать «разрывом» 
   или «ослаблением» — условие чёткое: каждый день, 27 дней, из одного 
   города.

Ограничения
1. Мало результатов. Большинство пользователей не пишут каждый 
   день. Поэтому home_city будет null у большинства. 
   Это осознанное ограничение — выбрана точность вместо 
   покрытия.
2. Пользователь, который регулярно 
   ездит между двумя городами (например, живёт в Москве, работает 
   в Подольске), не получит home_city — потому что не пишет 
   каждый день из одного города.
3. Если depth < 27 (в sandbox-контуре depth=3), home_city 
   не рассчитывается — данных недостаточно. Полноценный home_city 
   появится на depth ≥ 27.
4. Возможное уточнение. Если по итогам проверки окажется, что 
   условие слишком строгое и home_city находится у слишком 
   малого числа пользователей, можно рассмотреть ослабление:
   - «писал каждые 2–3 дня» вместо «каждый день»,
   - или «разница между первым и последним сообщением ≥27 дней»
   - или другие варианты на усмотрение заказчика

### travel_array и travel_count
travel_array — список городов в порядке посещения.
travel_count — количество посещений.

Правило схлопывания
Идущие подряд повторы (когда пользователь находился в одном городе
несколько дней) схлопываются в одно посещение.

Возврат в город после другого города считается новым посещением.

Примеры:

| Сырой список городов        | travel_array                | travel_count |
|-----------------------------|-----------------------------|--------------|
| Sydney, Sydney, Melbourne   | Sydney, Melbourne           | 2            |
| Sydney, Melbourne, Sydney   | Sydney, Melbourne, Sydney   | 3            |
| Sydney, Sydney, Sydney      | Sydney                      | 1            |
| Sydney, Melbourne, Sydney, Melbourne | Sydney, Melbourne, Sydney, Melbourne | 4 |

Это соответствует условию задачи: «Если пользователь побывал в
каком-то городе повторно, то это считается за отдельное посещение».

### Обработка времени событий
При анализе данных обнаружена систематическая особенность: поле 
event.datetime заполнено только у канальных сообщений 
(event.message_channel_to заполнено). У личных сообщений 
(event.message_to заполнено) event.datetime всегда null, 
а вместо него заполнено поле event.message_ts.

Что показывает message_ts
Поле message_ts содержит корректное время события, но с 
систематической ошибкой в годе: у личных сообщений год записан 
как 2021, тогда как реальный период данных — 2022.

Проверка показала: месяц, день и время в message_ts совпадают 
с датой партиции (date) и с полем datetime у канальных сообщений. 
Различается только год — сдвиг на -1.

Решение
Для построения витрин используется единое поле времени события, 
рассчитываемое через coalesce:
F.coalesce(
    F.to_timestamp("event.datetime", "yyyy-MM-dd HH:mm:ss"),
    F.to_timestamp("event.message_ts") + F.expr("INTERVAL 1 YEAR")
)
Пояснение:
F.add_months и F.date_add обнуляют время до 00:00:00,
так как работают с типом date. Для сохранения времени используем
+ INTERVAL 1 YEAR — это корректная операция над timestamp

Логика:
- Если event.datetime заполнено (канальные) — используем его.
- Если нет (личные) — используем event.message_ts со сдвигом 
  года на "+1" (2021 → 2022).

Обоснование
1. Не теряем 90% данных. Если бы мы использовали только datetime, 
   в расчёт попали бы лишь канальные сообщения (~4–10%). Личные 
   сообщения — большинство, и они тоже «исходящие», то есть 
   участвуют в геоаналитике.
2. Сдвиг года обоснован. Тест показал, что месяц/день/время в 
   message_ts совпадают с датой партиции. Это значит, что 
   message_ts — реальное время события, а год — особенность данных.
3. Устойчивость к изменениям данных. Использование coalesce 
   позволяет коду работать и в будущем, когда данные дозаполнятся:
   - если у личных появится datetime — coalesce возьмёт его;
   - если нет — продолжит использовать message_ts + сдвиг.

Ограничение
Подход основан на предположении, что сдвиг года в message_ts — 
систематическая ошибка, а не отражение реального периода. 
Обоснование — совпадение месяца/дня/времени с датой партиции.

## Витрина зон
### Определение зоны события

Для агрегации событий по городам (zone_mart) нужно определить 
зону (город) каждого события.

Источники координат:

- message — свои координаты lat/lon (пользователь физически 
  отправлял сообщение из точки).
- reaction и subscription — координаты последнего 
  отправленного сообщения пользователя за период расчёта.

Ограничение: 82% событий без координат:

В данных выявлена существенная особенность: большинство пользователей, 
совершающих reaction и subscription, не отправляют сообщений 
в том же окне расчёта.

Цифры за 3 дня:
- message: 17 018 событий, 7 916 уникальных пользователей;
- reaction: 39 726 событий, 35 395 уникальных пользователей;
- subscription: 73 619 событий, 56 393 уникальных пользователей.

Пересечение пользователей — только 7 916 (те, кто писал сообщения). 
Значит:
- 100% message получают координаты (свои).
- ~17% reaction/subscription получают координаты 
  (у кого есть сообщения за период).
- ~83% событий остаются без координат и исключаются из zone_mart.

Решение:

Следуя буквальной формулировке задания («присвойте координаты 
последнего отправленного сообщения»), мы не выдумываем координаты 
для событий без сообщений. Такие события исключаются из витрины.

Возможное уточнение:

Если заказчику потребуется большее покрытие, можно рассмотреть:
- расширение окна расчёта (например, «последнее сообщение за всё 
  время» вместо «за период»),
- заполнение координат по последнему известному местоположению 
  пользователя (вне окна).

# При расчете применено кэширование 

В процессе работы над витринами выявлена особенность Spark: 
row_number() неоднозначен при равных значениях 
в orderBy().

Где применено:
- events_with_zone — в main() после add_zone_id_to_events.
- first_message — в build_zone_mart. 
- pairs_with_dist — в build_friend_mart.
- pairs_both — в build_friend_mart.

Пример: если у пользователя два сообщения с одинаковым 
event_time, но разными координатами — row_number() 
может выбрать любое из них при разных запусках.

Решение: 
кэширование дорогих DataFrame (.cache() + .count()), 
которые используются несколько раз. Это фиксирует результат 
одного расчёта и обеспечивает согласованность всех 
последующих операций.

Пример: при расчёте friend_mart на 30 днях фильтр ≤1 км давал 
4 пары при одном вызове count() и 5 при другом — из-за пересчёта 
pairs_with_dist без кэша. Оба варианта — корректны. Разница из-за того, какое сообщение выбралось 
как последнее у некоторого пользователя (с одинаковым event_time).После добавления .cache() результат 
стабильно 5.
